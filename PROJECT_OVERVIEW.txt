2. OBJECTIFS

Le projet fournit une plateforme de fidélite complete pour les ventes
professionnelles B2B, les ventes B2C, le commerce en ligne et le point de
vente. Ses objectifs sont :

- afficher et attribuer des cartes de remise;
- calculer automatiquement les remises;
- cumuler les points de fidélite;
- promouvoir les clients vers les tiers supérieurs;
- appliquer les remises sur le web, les ventes, les devis et le POS;
- proteger les avantages contre les abus et les doubles utilisations;
- suivre le comportement commercial des clients;
- produire des analyses RFM, CLV, churn et d'association Apriori;
- fournir des tableaux de bord commerciaux et opérationnels;
- sécuriser les données sensibles et les opérations administratives;
- automatiser les tests, les scans de sécurité et le déploiement.

6. TIERS DE FIDELITE

Bronze :
- remise : 2%;
- niveau par défaut à l'inscription;
- seuil : 0 TND depense / 0 point.

Silver :
- remise : 5%;
- seuil alternatifs : 40 000 TND depensés sur les 30 derniers jours;
- ou 4 000 points cumulés.

Gold VIP :
- remise : 10%;
- seuil alternatifs : 60 000 TND depensés sur les 30 derniers jours;
- ou 6 000 points cumulés.

Platinum :
- remise : 16%;
- seuil alternatifs : 100 000 TND depensés sur les 30 derniers jours;
- ou 10 000 points cumulés.

La règle métier utilise le seuil atteint soit par depense glissante, soit par
cumul de points. Chaque client conserve une seule carte active correspondant
au plus haut niveau obtenu. La montée en niveau ne doit pas créer plusieurs
cartes actives simultanées.


7. POINTS ET EARNING RULE

La règle commerciale recalibrée est :

10 TND dépensés = 1 point de fidélité

La formule est fondée sur amount_total / 10.0 pour les déductibles.
L'acquisition s'applique de manière cohérente à :

- commandes boutique / website;
- devis et commandes Sales;
- commandes POS;
- factures validées;
- paiements complets selon les règles configurées.

Les points ne sont pas simplement recalculés à l'affichage : ils sont produits
par les modèles du programme, enregistrés dans les données client et utilisés
par les conditions d'attribution des cartes.


8. CARTES DE FIDELITE

9. FLUX DU CLIENT PORTAIL

1. Le client ouvre l'application ou utilise l'inscription / login.
2. Odoo vérifie l'utilisateur et la relation partner.
3. L'utilisateur accede à /my/cartes.
4. Le système récupère la carte active la plus élevée.
5. Il affiche le solde de points.
6. Il calcule les deux prochaines cibles Silver, Gold ou Platinum.
7. Il affiche les bars de progression en depense 30 jours et en points cumulés.
8. Il affiche les avantages, les récompenses et les notifications.
9. Le client peut initier ou consulter une vérification QR/OTP selon les droits.

Les résultats sont disponibles pour les clients autorisés par les record rules.
Un visiteur anonyme est redirigé vers /web/login.


10. FLUX DE LA BOUTIQUE

1. Le client parcourt /shop.
2. Il sélectionne des produits de mobilier de bureau.
3. Odoo applique les listes de prix et la fiscalité tunisie TND.
4. Le solde de la carte est détecté pour l'utilisateur.
5. Une remise valide est appliquée au panier ou à la ligne.
6. Le panier affiche le montant TTC et la remise calculée.
7. Le paiement d'essai ou réel est utilisé.
8. La commande est confirmée.
9. Les points sont recalculés.
10. Les règles de tier peuvent promouvoir le client.
11. Les statistiques omnicanales sont recalculées.
12. Une notification ou un e-mail peut être envoyé.


11. FLUX DE VENTE SALES

1. Un utilisateur Sales crée un devis ou une commande.
2. Il sélectionne un partenaire B2B.
3. Les lignes produisent les quantités, prix et TVA.
4. La carte active du partenaire est recherchée.
5. La remise applicable est contrôlée côté serveur.
6. Le devis peut être confirmé.
7. Une facture peut être créée pour la commande validée.
8. Les paiements comptables confirment la réalisation commerciale.
9. Les points et statistiques sont recalculés.
10. Le partenaire peut monter de tier.


12. FLUX POS

1. caissier.sotufab ou un caissier autorisé ouvre une session POS.
2. Le caissier sélectionne les produits.
3. Le partenaire ou client est identifié.
4. Les cartes disponibles sont affichées.
5. Une vérification OTP ou QR peut être demandée.
6. Le serveur compare le digest signé et le nonce.
7. Une seule utilisation est autorisée selon le cooldown.
8. Le POS applique la remise validée.
9. Le paiement est enregistré.
10. La commande POS devient paid.
11. Les points, cumulés et tiers sont recalculés.
12. Le paiement, la carte et l'audit sont liés.

La vérification POS ne demande pas de PIN personnel. Elle utilise des mécanismes
de challenge, de digest constant-time, de nonce et de verrouillage PostgreSQL.
Les doubles dépenses sont protégées par FOR UPDATE NOWAIT et une fenêtre
temporelle.

15. ANALYTICS

Le module produit plusieurs vues analytiques :

- achats totaux;
- achats website;
- achats POS;
- achats Sales;
- nombre de commandes;
- fréquence d'achat;
- dernier achat;
- anciennete;
- montant moyen;
- CLV prédit;
- risque de churn;
- score RFM;
- top partenaires;
- répartition des tiers;
- produits associés;
- règles Apriori;
- support;
- confiance;
- lift.

RFM :
- récence;
- fréquence;
- montant monétaire.

CLV :
- la valeur CLV sur 12 mois est une estimation;
- elle utilise l'ordre moyen, la cadence annualisée et la probabilité de départ;
- elle ne représente pas automatiquement un bénéfice comptable.

Churn :
- la probabilité de churn combine le dernier achat, l'anciennete,
  la fréquence et la récence;
- les comptes sans activité récente deviennent des comptes à risque;
- les nouveaux acheteurs peuvent avoir un score distinct.


16. APRIORI

Apriori extrait les associations entre produits confirmés.
Les données sources sont :

Chaque résultat donne :

- produits antecedents;

- confiance;
- lift;
- règle manuelle ou générée;
- date de recalcul.

Les bundles récurrents de mobilier de bureau sont utilisés pour améliorer les
règles croisées et les suggestions du POS.

19. MODELE ML

Le modèle CLV/churn est entraîné sur les données historiques.
Les datasets de base sont :

- ml_model/dataset_achats.csv;
- ml_model/dataset_clients.csv.

Le script principal est :

- ml_model/train_recommendation.py.

L'artefact sauvegardé doit être vérifié avant chargement.
Son SHA-256 doit être enregistré dans le paramètre restreint
cartes_reduction.ml_model_sha256 ou dans la variable
CARTES_ML_MODEL_SHA256.

Si le modèle est modifié, son checksum doit être recalculé.
Le chargement échoue fermement en cas de checksum manquant, invalide ou
différent.
Chaque échec peut générer un événement d'audit.

23. NGINX

Nginx agit comme reverse proxy HTTPS devant Odoo.

Fonctions prévues :

- TLS 1.2 / TLS 1.3;
- redirection HTTP vers HTTPS;
- proxy_pass vers Odoo;
- headers de sécurité;
- compression;
- limites de taille upload;
- keepalive;
- static cache;
- healthcheck;
- restriction administrative;
- protection des endpoints sensibles.

Nginx ne remplace pas le firewall ni les record rules Odoo.
Le port backend 8069 ne doit pas être exposé directement à Internet.

Exemple conceptuel :

server {
    listen 443 ssl;
    server_name domaine.example;

    location / {
        proxy_pass http://127.0.0.1:8069;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

25. BANDIT

Bandit analyse le code Python du module pour détecter :

- eval / exec;
- shell et subprocess;
- secrets codés en dur;
- hash faibles;
- pickle unsafe;
- asserts;
- désérialisation unsafe;

Les résultats sont classés par confiance et gravité.

acceptation documentée.

Commande exemple :
